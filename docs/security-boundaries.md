# Runtime catalog security boundaries

## Offline signer ceremony

`catalog-sign` is an inner Linux x86_64 signer. Direct execution is unsupported and fails before identity lookup, argument collection, transfer parsing, output preflight, or key access. Its first operation is `enter_signer_isolation()`, whose first process controls set and verify `PR_SET_DUMPABLE=0` and inherited soft/hard `RLIMIT_CORE=0`. The launcher establishes both core limits before opening a key; the inner prctl is separately required because exec may restore dumpability.

A launcher marker is not authority: the inner process also proves no-new-privileges, an already-active launcher seccomp filter, PID 1, zero effective/permitted/inheritable/ambient capabilities, the exact sanitized environment, empty mode-0700 `/home/signer` and `/tmp`, a loopback-only namespace with no route, and the exact mount topology. `/` is the current-owner mode-0555 Bubblewrap `/newroot` tmpfs with exact `rw,nosuid,nodev,relatime` VFS options; task mounts are direct children and device mounts are children only of private `/dev`. Host namespace strings are cross-checks only. PID 1, the private tmpfs root, the loopback-only route state, zero capabilities, and prefilter syscall outcomes provide kernel/outcome authority for the PID, mount, network, and user isolation boundaries.

The actual launcher filter denies socket/network, io_uring setup/entry/registration, fork/vfork/clone/clone3, ptrace, and namespace/mount mutation while permitting the single exec into the static signer. Before installing the inner filter, the signer safely proves the inherited launcher policy: socket/connect/fork/io_uring and selected namespace/mount calls return `EPERM`; an unexpected fork child is reaped; and exec of a fixed nonexistent path returns `ENOENT`, proving the final exec denial is not yet active. The inner signer then installs an architecture-checked classic-BPF filter returning `EPERM` for that family plus `execve` and `execveat`. x32 and non-x86_64 syscall ABIs fail closed. The real-launcher `isolation-probe` ceremony has no key mount, records both prefilter and postfilter results, and cannot select signing behavior.

The only inner task-data mounts are:

- read-only `/input` and writable fresh `/output` for every ceremony;
- read-only `/key/runtime-catalog-private.pem` only for `sign`;
- no `/key` mount or key interface for `assemble-intent` or `finalize`.

The static signer receives no repository, system tree, user home, SSH state, GitHub configuration, credential store, proxy, token, SSH-agent, or ambient file descriptor authority. `/proc` and `/dev` are minimal private Bubblewrap mounts. The repository and production key must never be mounted.

## Launcher configuration and executable identity

The launcher accepts only these exact ordered forms:

```text
catalog-sign-launcher assemble-intent --config CONFIG --input BUNDLE --output FRESH_OUTPUT
catalog-sign-launcher finalize        --config CONFIG --input BUNDLE --output FRESH_OUTPUT
catalog-sign-launcher sign            --config CONFIG --input BUNDLE --key EXPLICIT_KEY --output FRESH_OUTPUT
catalog-sign-launcher recover-sign    --config CONFIG --input BUNDLE --output EXISTING_OUTPUT
catalog-sign-launcher isolation-probe --config CONFIG --input BUNDLE --output FRESH_OUTPUT
```

`CONFIG` is canonical JCS JSON, one-link regular mode `0600`, current-owner, at most 16 KiB, and has exactly:

```json
{"bwrap_path":"/usr/bin/bwrap","bwrap_sha256":"64 lowercase hex","schema_version":1,"signer_path":"/absolute/static/catalog-sign","signer_sha256":"64 lowercase hex"}
```

Paths are canonical absolute paths opened component-by-component without links. `/usr/bin/bwrap` must be root-owned, one-link mode `0755`, executable, bounded, and match its full configured SHA-256. The signer must be current-owner, one-link mode `0500`, bounded, match its full configured SHA-256, and parse as x86_64 ELF64 with load segments and no `PT_INTERP` or `PT_DYNAMIC`. Production ceremony builds it outside isolation with:

```bash
rustup target add x86_64-unknown-linux-musl # public one-time prerequisite when absent
RUSTFLAGS='-C target-feature=+crt-static -C relocation-model=static' \
  cargo build --locked --release --target x86_64-unknown-linux-musl \
  -p catalog-sign --bin catalog-sign
```

The launcher retains exact bwrap, signer, input-root, optional key, output-root, and seccomp descriptors. It hashes and rebinds named executable identities before key open, immediately before output visibility, and immediately before launch; Bubblewrap binds the retained descriptors rather than reopening task paths. Tests synchronize at three private `cfg(test)` checkpoints immediately before signer open, after retained signer authentication, and immediately before the final bind recheck. Those checkpoints have no environment, CLI, feature, or release-binary surface. Output is a missing absolute child of a retained current-owner mode-0700 directory and is created once as mode `0700`. The explicit key is opened only after signer/input admission, without links, and must remain a current-owner one-link regular mode `0400` or `0600` file. No key bytes or key digest enter configuration, output, logs, or attestation.

Bubblewrap is invoked directly, never through a shell, with fixed arguments: `--unshare-all`, `--unshare-net`, `--die-with-parent`, `--new-session`, PID 1, `--clearenv`, capability drop, descriptor binds, private mode-0555 tmpfs root, private home/tmp, minimal proc/dev, fixed cwd, fixed locale/timezone, and the launcher seccomp descriptor. Child stdout/stderr are suppressed and the launcher emits only a fixed success or fixed failure line.

## Authenticated transfer

Before launch, the Task 6 signer verifier reopens the complete online-to-offline `transfer-manifest-v1.json`, all records, and every digest-addressed object through retained descriptors. Extra, missing, linked, replaced, writable, oversize, wrong-mode, wrong-size, wrong-digest, or identity-rebound content fails before key open and before output creation. The SHA-256 of the exact canonical transfer manifest is injected into the isolated process. Isolation verifies `/input` once through `verify_transferred_bundle`, compares that retained manifest digest to the launcher-attested digest, and stores the same retained `VerifiedTransferredBundle` inside a non-constructible `SignerIsolation` capability. Assembly, finalization, and signing consume only that retained bundle and its retained record/object descriptors; they do not reopen `/input` through a path CLI.

After a successful inner command, the signer writes a fresh canonical `transfer-manifest-v1.json` in `/output`. It covers every public output regular file with relative path, exact `0400` mode, size, and SHA-256, contains no host path, and binds the input-transfer digest and complete `IsolationAttestationV1` including both the original operation mode and actual completion mode. The reverse manifest is settled through an unnamed file and one no-clobber link; an exact existing manifest is canonically reopened and accepted, while partial or conflicting bytes are never replaced. The output root and any signed-bundle directory are exact mode `0700`; all publication objects and the reverse manifest are exact mode `0400`, one-link, current-owner files. Existing names are never replaced. Task 8 independently reopens and verifies this reverse bundle before publisher authority is possible.

Signed payload publication has an explicit post-visibility state. Before publication can become visible, the canonical operation binding is durably extended with the exact random stage relative name, device/inode, owner, mode, and cleanup-authorization state. Once the no-clobber payload rename succeeds, every cleanup path first reopens and verifies the exact visible bundle with the appropriate compiled public identity. Parent-fsync failure is reported as durability uncertainty rather than durable success. Recovery opens only that bound name descriptor-relatively without following links, compares its exact identity and owner/mode, requires it to be empty, and never scans for a convenient matching stage. Missing, replaced, unbound, nonempty, invalid-output, or otherwise uncertain evidence is preserved and fails closed. The keyless `recover-sign` ceremony reauthenticates the same config signer, retained input digest, original `sign` operation, isolation boundary, and existing output root, recomputes the expected candidate, verifies the visible production- or fixture-signed bundle through public verification, settles only the exact bound stage, and idempotently completes or accepts reverse manifests whose actual completion mode is schema-authorized as `sign` or `recover-sign`. It never opens a key, resigns, overwrites, or admits a different candidate.

## GitHub CLI credential broker

The harmless fixed `transport-v1` prerelease has a dedicated owner-private mode-`0700` `TransportWorkflowState`; it never opens or verifies the production or fixture catalog authority and requires no signed catalog, signing key, production signature, latest catalog reference, package asset, or production operation. The fixed root layout contains empty `objects/` and `latest/`; only the descriptor-bound mode-`0600` `.remote-workflow-v1.lock` and canonical mode-`0400` `transport-operation-v1.json` and `transport-receipt-v1.json` are admitted in `latest/`. Persistent state directories accept either their conventional exact link count or `1` as reported by Btrfs, overlay, and large-directory filesystems; exact bounded enumeration, allowed child names, owner, mode, descriptor identity, and per-child validation remain mandatory, while regular-file link counts remain exact. State records prefer `O_TMPFILE` plus a no-clobber link. Only `EOPNOTSUPP`/`ENOTSUP` or `EINVAL` indicating unsupported `O_TMPFILE` permits direct final-name `O_CREAT|O_EXCL|O_NOFOLLOW` creation; that path writes mode `0600`, flushes, changes to exact `0400`, fsyncs file and parent, then reopens and compares identity, owner, one-link mode, size, and exact bytes. Existing names and every other open/write/readback error fail closed, and this fallback has no rename, delete, cleanup, or overwrite authority. A crash or short write preserves the partial final record and grants no remote authority. After owner review, a fresh dedicated transport state can settle the same exact public operation because its operation identity is state-path-independent; the partial state is never deleted. Unknown, temporary, production, and latest records fail closed before broker authority. The canonical operation binds exactly the fixed repository, reviewed source commit, compiled manifest SHA-256, broker-client config SHA-256, broker executable SHA-256, and inner broker config SHA-256. One retained exclusive lock spans every decision, durable pre-mutation operation write, remote mutation, exact readback/recovery settlement, and receipt write. Production `stage-remote`, `approve`, `publish`, and `verify-latest` continue to open and verify the production-signed Task 8 state without weakening.

The publication workflow reaches authenticated authority only through a separate `catalog-gh-broker` process launched by `broker_client.rs`; it never calls the broker implementation in-process and never opens the GitHub configuration directory. The exact owner-private mode-`0600` canonical `PublisherBrokerClientConfigV1` contains only `schema_version`, canonical absolute `catalog_gh_broker_path` plus its lowercase SHA-256, and canonical absolute Task 9 `publisher_broker_config_path` plus its lowercase SHA-256. It contains no token, credential, GitHub config-directory, repository, route, or network authority. The client opens every component without links; user-owned ancestors must be exact mode `0700` or `0755` (while the root-owned ancestor allowlist is unchanged), so `0750`, `0751`, writable, and every other user-owned mode fail closed. It retains and rebinds the client config, executable, and Task 9 config by exact owner/mode/link/size/hash/identity before and after every request, validates the broker as x86-64 ELF, and executes only the retained `/proc/self/fd/N` descriptor. Its environment is cleared, stdin/stdout/stderr are bounded, stdout is accepted only as canonical typed `BrokerResponseV1`, stderr is never projected, and timeout/failure kills and reaps the dedicated broker process group.

`catalog-gh-broker` is the publisher's sole authenticated process-launch boundary. It accepts only exact ordered `--config CONFIG --expected-config-sha256 HEX`, then one bounded canonical `BrokerRequestV1` on stdin. It opens the Task 9 configuration once and rejects a canonical-byte digest mismatch before opening the configured gh executable, GitHub configuration directory, or child-process authority. The request family is closed to `create_tag`, `read_tag`, `create_draft`, `read_draft`, `upload_asset`, `download_asset`, and `publish_draft`; it contains no method, route, host, header, argument, query, template, GraphQL, authentication, token, shell, Git, or environment field. Repository, production/transport tag, full commit, decimal ID, title, notes, prerelease, asset-name, and absolute asset-path fields validate before the broker opens its config or process capabilities.

The canonical owner-private mode-`0600` Task 9 `PublisherBrokerConfigV1` contains only schema version, canonical absolute `gh_path`, exact lowercase executable SHA-256, and canonical absolute `github_config_dir`. The broker opens every component without links; user-owned ancestors and the retained/rebound current-owner GitHub config directory admit only exact mode `0700` or `0755`, with the root-owned ancestor allowlist unchanged. The broker never lists or reads credential files, and config/credential regular files remain exact mode `0600`, one-link, and unread by the publisher. The configured executable is a retained one-link regular executable owned by root or the current user, is never group/world writable, and is fully rehashed and named-rebound immediately before spawn. It must parse as bounded Linux x86-64 little-endian ELF64 with valid program headers and executable load segments; dynamically linked and interpreter-bearing normal executables are allowed. Scripts and shebangs are rejected. Execution is exclusively through the retained `/proc/self/fd/N` capability, with executable and config-directory CLOEXEC state cleared only in the post-fork child. There is no named executable fallback and no `PATH` discovery.

Each invocation creates a new empty mode-`0700` HOME and clears the entire child environment. Fresh empty broker-private directories accept only conventional link count `2` or the portable directory count `1`; exact emptiness, owner, mode, and retained identity checks are unchanged, and all broker regular files remain one-link. The only child variables are `HOME`, retained `/proc/self/fd/N` `GH_CONFIG_DIR`, `LANG=C`, `LC_ALL=C`, and `TZ=UTC`. No token, proxy, SSH-agent, Git, Cargo/Rust, XDG, `PATH`, repository, user home, or SSH directory is inherited. Six of the seven typed requests map to fixed no-shell `gh api` REST argument arrays with fixed methods, routes, headers, and canonical JSON bodies. Upload maps only to `gh release upload TAG PRIVATE_EXACT_FILE --repo OWNER/NAME` without `--clobber`. Its exact validated tag is the sole remote upload authority: `UploadAsset` has no release-ID field and `AssetUploaded` returns none. The broker never invokes authentication/token commands or accepts arbitrary arguments, routes, methods, hosts, headers, or query strings.

Immediately before the retained executable is entered, the broker sets and verifies a `PR_SET_PDEATHSIG=SIGKILL` binding to the exact broker PID, then establishes a Linux x86-64 seccomp filter with `no_new_privs`. Thus an outer broker-client timeout cannot strand gh even though gh has its own supervised process group. Architecture mismatch, a nonzero clone-flags high word, and x32 syscalls fail closed. `fork`, `vfork`, `clone3`, process-form `clone`, `setsid`, `setpgid`, namespace entry/creation, and old/new mount mutation syscalls return `EPERM`. Classic BPF requires all of `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_SYSVSEM|CLONE_THREAD` and permits no other low-word bits except `CLONE_SETTLS`, `CLONE_PARENT_SETTID`, `CLONE_CHILD_SETTID`, and `CLONE_CHILD_CLEARTID`; these optional bits provide only thread-local TLS and TID-address metadata. This compatibility policy is pinned to offline evidence: the intended Fedora `gh` 2.97.0-2.fc44 `/usr/bin/gh` has SHA-256 `16fdbf30d6f97bc5b0fb94745e00fa06ae68beb6c6653d7f584b32602800397d` and reports Go build `go1.26.5`; official `go1.26.5/src/runtime/os_linux.go` defines the bare base set, while official `go1.26.5/src/runtime/sys_linux_amd64.s` adds `CLONE_SETTLS` for normal `newosproc` when m/g are non-null and leaves `newosproc0` able to use the bare set. That runtime uses `SYS_clone`, not `clone3`; `clone3` remains denied because this filter has no separately inspectable thread-only argument policy. The filter permits the initial retained `execve`, persists across every later exec, and does not deny the fixed commands' network or file syscalls. On every outcome, including apparent child success, the broker sends `SIGKILL` to the original process group, uses only nonblocking `try_wait` through the established deadline, and proves both leader reap and process-group absence. An exceptional unresolved leader is handed to a detached reaper without delaying the API; no successful request can leave a process able to retain `GH_CONFIG_DIR`.

The transport phase has one explicit hard deadline: 120 seconds in production. One poll-based nonblocking state machine supervises child stdin, stdout, stderr, leader status, descendant-held pipes, and anonymous download-spool writes from a deadline established before spawn. JSON stdout is capped at 128 KiB and stderr at 64 KiB; the first overflow byte, timeout, signal, nonzero exit, malformed/duplicate output, projection mismatch, or a retained pipe kills the complete process group, closes broker pipe ends, and produces only `github broker failed`. Download stdout is always piped through the broker into a bounded anonymous memfd, incrementally counted and hashed, and is never written past the fixed asset ceiling. The child never receives the final output descriptor.

Only after gh and its process group are absent and credential capabilities are closed does download enter its separately named 120-second production settlement phase. A dedicated forked helper copies the sealed spool into the retained fresh no-clobber mode-`0600` output, incrementally checks size and SHA-256, fsyncs, changes to mode `0400`, fsyncs again, reads back, and named-rebinds. After that helper succeeds and before success is recorded, the broker reopens the stored absolute parent component-by-component without following links, compares the retained and canonical parent's exact device, inode, owner, mode, and link count, then reopens the final leaf from that canonical parent and compares its exact settled inode, owner, mode, link count, size, SHA-256, and bytes against both the retained output and sealed spool. Parent rename/replacement or mode drift and leaf replacement therefore fail closed. The broker polls the helper with `waitpid(WNOHANG)`, reserves time for `SIGKILL` and reap, and never performs the potentially blocking regular-file write/fsync itself. Failed or timed-out settlement invokes a separate bounded 10-second exact-inode cleanup helper against only the retained old parent; it removes only the exact retained partial/final inode and cannot touch a canonical replacement. If cleanup itself cannot settle, that inode is preserved rather than blocking or risking a replacement. Thus a download advertises separate hard bounds for transport, settlement, and exceptional exact-inode cleanup, with no blocking wait after any phase deadline.

For upload, the broker first authenticates the owner-private mode-`0400` source descriptor, then copies its verified bytes into a fresh broker-owned mode-`0700` per-request directory under the exact validated asset filename. That mode-`0400` no-clobber file is fsynced, hashed, read back, and rebound immediately before spawn; no host input pathname or upload descriptor is inherited. Success returns only typed `asset_uploaded` status with exact name, size, and SHA-256. Task 10 must execute exact `read_draft(tag)` immediately before and immediately after every upload, bind the returned release ID, tag, target commit, and draft state on both sides, and treat any call failure or field change as remote uncertainty. The broker does not claim ID-bound upload and never fabricates a remote asset ID. Neither child bytes, credential/config canaries, request content, nor host paths are echoed.

## Capability split

- `catalog-acquire`: generic public credential-free network acquisition; no signing-key interface.
- `catalog-latest-transport`: only the async fixed runtime-catalog latest endpoint and typed exact-byte result/error; no URL, origin, method, header, redirect, cache-path, credential, or generic fetch constructor input. It uses no proxy, no credentials, Rustls, the exact GitHub to release-assets origins, and never creates or blocks on a Tokio runtime.
- `catalog-sign-launcher`: the sole signer-side process-launch capability; fixed Bubblewrap only.
- inner `catalog-sign`: private-key parsing/signing requires the non-deserializable, non-constructible `SignerIsolation` capability returned only after every inner check and final-filter installation; raw signing and raw CLI entry points are not exported. Public library APIs retain only inert transfer verification and unsigned assembly/finalization contracts. The denied-syscall probe also requires the capability and has no key mount.
- `catalog-publish`: public bundle verification and publication; no private-key parser or key interface.

Committed fixture keys remain nonproduction test authority only. `catalog-sign-fixture` is a separately named static binary behind the nondefault `fixture-tools` feature. It reads only the committed fixture key identity, emits `catalog-test-key-v1`, verifies through the fixture public identity, and is rejected by production public verification; neither its entry point nor fixture identity is present in the default production signer binary. Its real Bubblewrap journey uses the same retained transfer, domain-separated catalog/release signatures, staging writer, reverse emitter, launcher, mounts, seccomp, recovery, and no-clobber implementation. Boundary mutations fail if fixture authority enters the production main or launcher surface.

The exact approved public assemble/finalize journey is intentionally ignored unless `CATALOG_AUTHENTIC_PUBLIC_CORPUS` names an explicit authenticated public corpus. `scripts/authentic-candidate-oracle.py` independently verifies the complete duplicate-free, bounded public transfer and constructs the catalog-v1 projection directly from its committed release intent without importing or invoking catalog-sign; its frozen expected candidate is 55,797 bytes with SHA-256 `7dba62c8b44883cbd7b3615fd9fe3b1a08a3aa2c75c7729704c14804d1cc2a2b`. `scripts/run-authentic-signing-journey.sh` exports retained transfers through the existing ignored reader, runs both normal production static-signer launcher ceremonies, and requires both real Bubblewrap candidates to equal the independent oracle byte-for-byte and match that digest before proving no-clobber. The producer has no Fluxsemble code, build, test, or runtime dependency. The production private key, SSH directories, remote publication credentials, and repository mutation are outside this boundary and are never used by automated tests.
